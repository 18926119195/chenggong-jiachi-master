# 实验结论：定位算法对比与 s1 API 兜底必要性验证

## 实验目的

验证是否需要使用定位算法 2、3 对 s1 LLM 提取的 non-high confidence 结果进行兜底，以及这些低置信度结果是否真的存在漏提取问题。

## 实验方法

1. 提取所有 s1 LLM 返回的 non-high confidence 条目（medium 和 low）
2. 对这些条目对应的原文截断进行人工逐条审查
3. 判断截断内是否真的包含被 LLM 漏掉的名词

## 实验结果

### 数据统计

- **总 non-high 条目数**: 384 条
- **人工判定为正确（截断内确实无名词）**: 371 条
- **人工判定为漏提取（截断内有名词但 LLM 未提取）**: 13 条

### 准确率

**96.6%** 的 non-high 条目都是正常的——截断里根本就没有名词，LLM 没有漏提取。

### 漏提取分布

13 条真实漏提取分布在 **5 个批次**中：
- batch_0_2026-09-21T05-50-32-340Z
- batch_11_2026-09-21T05-51-07-606Z  
- batch_18_2026-09-21T05-51-22-668Z
- batch_26_2026-09-21T05-51-40-527Z
- batch_4_2026-09-21T05-50-43-251Z

## 结论

### ❌ 不需要算法定位 2、3 兜底

这些 non-high confidence 截断里本来就没有名词可提取，使用定位算法 2、3 进行兜底是没有意义的。

**什么是定位算法 2、3？**
- **算法 1（当前使用）**: 仅在截断原始区间 `[truncStart, truncEnd)` 内精确匹配名词位置
- **算法 2（已废弃）**: ±N 字符扩窗搜索，在截断边界外寻找匹配
- **算法 3（已废弃）**: 全 chunk 兜底搜索，在整个 chunk 范围内寻找

实验证明算法 2、3 没有必要，因为 96.6% 的 non-high 结果都是正确的——截断内本就无名词。

### ❌ 不需要对 non-high 重跑 API

绝大多数（96.6%）non-high 结果都是正确的空结果，批量重跑会造成资源浪费。

### ✅ 只需针对性修正 5 个批次

只有 13 条（3.4%）真的有漏提取，涉及 5 个批次。如果要修正，只需要重跑这 5 个批次即可。

## 对正式流程的影响

基于以上结论，正式流程代码应该：

1. **移除定位算法 2、3 的相关代码** - 不再需要这些兜底机制
2. **简化 s1 结果处理逻辑** - 直接采用 s1 LLM 的提取结果，无需额外验证或兜底
3. **保持 s0 + s1 的二阶段架构** - s0 (spaCy) 粗提取 + s1 (LLM) 补缺已经足够
4. **保持 precision-first 策略** - 宁可少提取，也不要误匹配到其他上下文的同名词
